# Collector Pipeline

The local Collector config lives at `deploy/local/otelcol.yaml`.

That file is generated by:

```powershell
python scripts\generate_collector_config.py
```

Do not hand-edit `deploy/local/otelcol.yaml`. Change the registry or generator,
then regenerate the file.

The generator uses the merged upstream plus extension registry. Every known
attribute id becomes a `service_graph` dimension so service graph metrics can
carry enough context to reinforce the graph.

## Pipelines

The local Collector has two relevant pipelines.

The trace pipeline receives OTLP traces and exports them to:

- `service_graph`

The service graph metrics pipeline receives metrics from:

- `service_graph`

and exports them to:

- `kafka/servicegraph_metrics`

The Kafka exporter writes OTLP JSON metrics to topic
`otel.servicegraph.metrics`.

## Why service_graph Dimensions Are Broad

The project treats service graph metrics as graph events, not as a metrics
storage surface. The Collector writes the service graph metrics to Kafka as OTLP
JSON, and the graph loader turns those metric datapoints into graph
observations.

This is intentionally different from a production metrics backend, where broad
or unbounded dimensions can cause time-series explosion. If these metrics are
also exported to a metrics database later, use a separate metrics pipeline with a
bounded dimension set.

## Collector Safety Defaults

The generated config keeps `memory_limiter` first in each processor chain and
uses `batch` before export.

The local config is for development. A production deployment still needs the
normal OpenTelemetry Collector decisions around sticky routing for stateful
connectors, persistent queues, TLS, authentication, resource limits, and rollout
strategy.

## Version Compatibility

`docker-compose.yaml` pins `otel/opentelemetry-collector-contrib:0.156.0`.
The stock image does not include a `metrics_as_logs` or `metricsaslogs`
connector. The local pipeline intentionally avoids that component and exports
service graph metrics directly to Kafka with the Collector Kafka exporter.

## Validation

Run these checks after changing the Collector generator or registry attributes:

```powershell
python scripts\generate_collector_config.py --check
docker compose config
docker compose up --build
```

`docker compose config` proves the Compose file and generated Collector config
can be rendered together. `otelcol validate` is the stronger check for the
Collector binary itself.
